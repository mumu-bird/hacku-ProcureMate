## 本次实际修复

新增选品验证：先比较所有符合必要规格的组合，再筛预算内方案；不足三套时如实展示。支持最低容量、明确保温要求与最低完整现金支出偏好；规格只来自商品来源标题，未知信息不会被视为符合。报价与审计保存候选金额、排除原因、预算内数量和模型调用状态，付款前独立复核数量、需求预算与规格。

`npm run verify:integrations` 可重复验证真实模型以及 Stripe 测试授权、扣款、查询、退款与取消。当前运行结果两项均为 `not_configured`，退出码 2；不是集成通过。v0.2.0 录像与路演展示当前 45/5 软件验证结果；真人对照仍为空，不将工具验证视为真人数据。


1. **费用规则错误：** 原先统一加 HK$80，漏掉符合条件订单净额满 HK$400 的标准免运费。现按观察到的规则计算；报价保存规则来源、独立采集时间和页面摘要哈希。过时、无来源的旧报价必须重新生成。
2. **拦截故事失真：** 十人订单已满免运费门槛，不应加费制造异常。现在另建明确标注的单件小额测试，原采购人数和方案保持不变。
3. **支付状态竞态：** 成功回调先到、网络响应后失败时，旧状态可能覆盖已付款或已退款。现在读取最新状态，保留已确认结果；丢失的支付编号可由已验证事件恢复。
4. **支付结果核对：** 渠道返回金额或币种不一致时停止扣款并保留预算；已存在订单不能通过另一适配器查询或退款。并发核对只允许一个执行者发起扣款。
5. **审计链并发与导出：** 两个进程写日志时可能使用同一前序哈希；现将读取与插入放在同一写事务。界面保留 200 条显示上限，证据导出包含完整链。
6. **补货只演示了部分流程：** 原验证没有证明收货后领用能成功再次购买。现在负责人可确认累计预算和最短间隔；浏览器验证了第二笔授权内补货、在途去重和第二次收货。
7. **展示稳定性：** 外部字体请求导致页面加载卡住；现使用本机字体，正常展示不依赖字体服务。

## 实测结果

45 项核心测试全部通过，5 条浏览器流程全部通过，TypeScript 检查与生产构建通过。记录在 `artifacts/core-test-results.txt`、`browser-test-results.txt`、`browser-results.json`、`typecheck-results.txt`、`build-results.txt`。

新增回归测试曾复现费用、金额核对、支付回调竞态、编号恢复、渠道混用和跨进程日志错误；修复后通过。外部模型响应、支付事件与网络故障由本地测试夹具模拟，**不等于真实模型或 Stripe 集成验证**。测试只覆盖已执行的场景，不推导任意并发规模或绝对安全。

**优先顺序：** P0 完成人工对照、公开参赛代码与材料、补上第六页真实结果与正式提交；P1 真实模型推理与可行支付接入说明；P2 可用凭证下的 Stripe 沙箱核对。继续扩展商品数量、积分算法或视觉装饰的优先级较低。

人工对照材料见 `docs/user-study-protocol.md` 与空白 `docs/user-study.csv`。没有真实结果前，不填效率提升比例、企业客户或奖项概率。

## 支付可行性说明

比赛原型中，公司负责人在本地授予采购规则，支付适配器演示预授权、扣款、取消、查询和退款；测试订单可收货记账，但不存在真实商户履约。Stripe PaymentIntent 是本平台测试收款，并不是一个能替采购方任意在其他商户付款的公司钱包。

落地需要商户提供带商品、费用、有效期和订单标识的正式结账报价；公司支付账户由持有人按支付渠道要求授权，采购代理不能持有或扩大付款权限；奖励账户须属于公司且具备已核实资格。可先由代理生成订单并转到商户官方结账，由账户持有人确认付款，再取得可核对的支付和商户订单状态。自动付款则需要商户及支付服务明确支持受约束的委托接口。当前没有已确认的 HKT 接口或合作，不将接口存在作为商业承诺。

来源：公开派送规则 <https://shop.theclub.com.hk/shipping-policy?___store=en_US>；Stripe 测试与授权扣款 <https://docs.stripe.com/testing>、<https://docs.stripe.com/payments/place-a-hold-on-a-payment-method>。官方比赛权重与要求以工作区两份官方文件为准。
